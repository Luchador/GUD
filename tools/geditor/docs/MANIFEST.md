# GUD manifest

The manifest locates authored ROM data for tools. Adding an entry does not
change the game's asset loaders or enable asset import/editing by itself.

Search the big-endian `.z64` image on four-byte boundaries for the 16 bytes
`GUDGEDITORMANIF\0`. The following two `u32` values are the manifest version
and entry count. Each entry is four big-endian `u32` fields:

| Offset | Field | Meaning |
| --- | --- | --- |
| 0 | `kind` | FourCC |
| 4 | `romstart` | Inclusive ROM offset |
| 8 | `romend` | Exclusive ROM offset; zero only for documented self-terminating legacy kinds |
| 12 | `flags` | Kind-specific metadata; not a universal compression field |

The current version is 3. Ammo IDs now omit the redundant second 9mm type,
and `MultiAmmoCrateRecord` contains twelve slots (176 bytes total). IDs after
9mm shift down by one. Existing entry layouts are unchanged, but the version
bump prevents older readers from misinterpreting these setup resources.
Rebuild GUD and create a fresh project with the matching editor; old base ROMs
and setup files are not compatible.
There are currently 28 entries; the current GEditor accepts up to 32. The
16 new discovery entries below are optional to existing editor features.
Readers must find entries by kind rather than position and bounds-check even
unrecognized kinds. Changes to a catalog record layout require a new catalog
version; incompatible envelope changes require a new manifest version.

## Existing entries

`IMGS`, `OBSG`, `MUSF`, `STGT`, `CMAP`, `FTBL`, `ENVT`, `TXTB`, `TXCF`,
`MONA`, `MONT`, and `MOND` remain present. `STGT` already includes each level's
main music, ambient track and action track. `ENVT` includes sky/water and
visibility data as well as fog.

`CMAP` gives the ROM range and linked RAM base of the game's data segment.
For a linked RAM address `p`, resolve it as:

```text
rom_offset = CMAP.romstart + (p - CMAP.flags)
```

First require `p >= CMAP.flags`, then validate the offset and entire requested
span against `CMAP.romend`. A null pointer remains null. Do not translate RAM
pointers by simply stripping their high byte. Refer to project files using
the names and resource offsets in `FTBL`/`OBSG`.

## Native audio and animation ranges

| Kind | Range | `flags` | Interpretation |
| --- | --- | --- | --- |
| `SFXC` | `sfx.ctl` | 0 | Native sound-effect bank definitions |
| `SFXT` | `sfx.tbl` | 0 | Sound-effect sample bytes |
| `INSC` | `instruments.ctl` | 0 | Native music instrument bank definitions |
| `INST` | `instruments.tbl` | 0 | Instrument sample bytes |
| `MUST` | Music sequence directory | 8 | Four-byte header followed by eight-byte rows |
| `MUSD` | Music sequence payloads | 0 | Native `ALCSeq` sequences, including authored padding |
| `ANID` | `animation_data` segment | 0 | Animation headers, channel descriptors and packed root motion |
| `ANIF` | `animation_entries` segment | 0 | Expanded big-endian `u16` rotation frames generated by the build |

These ranges have no outer `1172` compression wrapper. Sound samples can
still use their native ADPCM encoding, and sequences retain the native event
encoding. `MUSF` covers the combined audio region; its stale `1172` flag is
now zero. Zero does not imply PCM sound, standard MIDI, or a decoded animation.

In each `.ctl`, follow the native `ALBankFile` structures (`PR/libaudio.h`).
Before the game's `alBnkfNew` fixups, non-null metadata pointers are offsets
from that `.ctl` start. Wavetable sample addresses are offsets from the paired
`.tbl` start. Loop records and ADPCM predictor books belong to the `.ctl`.
Validate every offset against the appropriate range.

`MUST` begins with `u16 seqCount` and `u16 reserved`. Each row is
`{ u32 offset; u16 uncompressed_len; u16 len; }`. The track ID is its row
index. `offset` is relative to **MUST's start**, not MUSD's start; `len` is
the stored byte length. The second length field is retained in the native
format and currently equals `len`. Validate each payload against `MUSD`.
The directory currently has 63 slots, including slot 0 (`M_NONE`).

Animation IDs require `ANIC` or `ANIO` below. Each valid catalog value is an
offset into `ANID`. At that header, offset 0 holds a frame-data offset into
`ANIF`; offsets 8 and 16 hold offsets into `ANID`. These are ROM-authored
offsets, before `expand_ani_table_entries` rewrites them into runtime pointers.
Read frame count, channel width and frame size from the header, using the
current `ModelAnimation` layout. Root-motion data remains packed. The full
segments are bounded, but individual headers/root-motion records have variable
lengths and must be decoded, not assumed to be an array of fixed-size structs.

## Catalog descriptors

Entries with `flags == GEDM_F_TABLE` (`0x80000000`) identify exactly one
16-byte `GedManifestTable` descriptor, not the records themselves:

| Offset | Field | Meaning |
| --- | --- | --- |
| 0 | `records` | Linked RAM address of the native array; resolve through `CMAP` |
| 4 | `count` | Number of addressable slots |
| 8 | `stride` | Bytes per native N64 record |
| 12 | `version` | Descriptor and per-kind record layout version, currently 1 |

Validate the version, expected stride and `count * stride` without integer
overflow, then require the whole record array to lie inside `CMAP`. Preserve
unused slots: removing them would renumber IDs. All pointers inside these
catalogs use `CMAP` except the documented ANIC/ANIO offsets and null values.

| Kind | Native array | Version-1 stride | Slot/termination rules |
| --- | --- | --- | --- |
| `MUSV` | `g_musicDefaultTrackVolume` | 2 | Signed 16-bit volumes; all 65 slots retained, including unused slot 63 and control value `0xffff` at 64. Playable track IDs come from MUST, not this count. |
| `ANIC` | `animation_table_ptrs1` | 4 | Character/player animation IDs; trailing zero excluded. Value 1 marks an unused slot and must not be dereferenced. |
| `ANIO` | `animation_table_ptrs2` | 4 | Object/vehicle animation IDs; trailing zero excluded. Same offset rules as ANIC. |
| `CHRM` | `CitemZ_entries` | 20 | Body and head model IDs; trailing terminator excluded. |
| `PROP` | `PitemZ_entries` | 12 | Prop model IDs; trailing terminator excluded. |
| `ITEM` | `gitem_structs` | 56 | Item/weapon IDs, including model-less items and reserved slots; no trailing terminator. |
| `AIGL` | `g_GlobalAILists` | 8 | `{ u32 scriptPointer; s32 ID; }`; the explicit ID is authoritative, not the row index. Trailing null record excluded. |
| `TXBK` | `g_TextBankNames` | 4 | Text-bank IDs map to NUL-terminated resource names; includes null slot 0, which is unused rather than a terminator. |

Current counts are emitted from `sizeof` beside the actual array definitions.
Readers must use these counts rather than the example counts in this document.

`CHRM` records contain a model-header pointer at 0, filename pointer at 4,
`f32 scale` at 8, `f32 pov` at 12, and four bytes at 16–19 (`isMale`,
`hasHead`, two padding bytes). `PROP` contains header/filename pointers at
0/4 and `f32 scale` at 8. Model headers in these tables are the game's header
templates; load model geometry by filename through `FTBL`, not by treating
the template as an already loaded model.

`ITEM` contains header/filename pointers at 0/4, `s32 has_no_model` at 8,
weapon-stat pointer at 12, two `u16` text IDs at 16/18, five floats at 20–36
(watch position and rotation), two text IDs at 40/42, and three equipment
position floats at 44–52. Some filenames and headers are null for valid item
IDs. The stats pointer is discoverable, but this manifest addition does not
define a new editable weapon-stat format.

`AIGL` locates shared bytecode programs. Script lengths are not in the native
rows: decode commands with their actual sizes and remain within CMAP. Level
scripts still come from their setup assets. `TXBK` names locate text resources
through `FTBL`; the mutable runtime `g_LangBanks` pointers are not exported.

## Builds and future editing

Rebuild GUD to embed these entries. A project keeps its own `base.z64`, so new
projects made from the rebuilt ROM will carry the new metadata. Existing
projects continue to work; their older base ROM will not gain the entries
just by saving or exporting it. GEditor needs no new UI or importer for this
discovery-only change. ROM creation preserves optional entries and their data.

Adding/replacing assets later must also update references and respect runtime
limits. Audio still has fixed buffers/counts and linker-address-based loading;
animation loading likewise has native pointer fixups and memory budgets. A
manifest entry does not make a bank freely relocatable. Keep existing IDs
stable and append new IDs only when the corresponding runtime supports them.

## Checks

After building the changed GUD objects with the normal N64 compiler:

```sh
python3 tools/geditor/tests/manifest_catalogs/run.py build/u
python3 tools/geditor/tests/current_formats/run.py
```

The first check inspects the actual big-endian MIPS object data and pointer
relocations. The second exercises GEditor's ROM/project reader and metadata
export with the extended manifest, including optional-entry preservation.
